Hacker Index

How the list is built, what it gets wrong, and how to check us.

The one rule

A thing ranks by how many different people recommended it — not by how many times it was mentioned. One person posting a title ten times is one person. This is the whole difference between a list and a signal.

Where the data comes from

The complete Hacker News archive: 49.3 million items, October 2006 to today, mirrored on Hugging Face as monthly parquet (open-index/hacker-news, ODC-BY). Every row here is a link somebody actually posted.

How an entity is found

  1. Links first. Every outbound URL in a story or comment is extracted. Older HN comments store some URLs HTML-escaped (http:&#x2F;&#x2F;…); those are unescaped before parsing, which recovers roughly 60% of links that a naive regex misses.
  2. The comment's own anchor text is the title. People link with the work's name, so we do not have to guess. For bare links the title is resolved afterwards from YouTube oEmbed, the iTunes lookup API, Steam's appdetails, Open Library (ISBN) or the arXiv API — results are cached in the repo.
  3. Keys are ids, not strings. ASIN, arXiv id, IMDb tt, Steam appid, YouTube id, owner/repo. A normalised URL is the fallback. We do not fuzzy-merge: a wrong merge costs more trust than a split.

How "recommended" is decided

Two passes. A keyword gate first — explicit praise only (recommend, worth reading, must-read, excellent…), plus story score ≥ 25 for submissions, since a submission's upvotes are the endorsement. Survivors then go to a cheap LLM that labels each comment recommend / critical / neutral with the comment body as context. Verdicts are stored with the model name and prompt version, so any number on this site can be traced back to the decision that produced it.

Every row links to the actual comment. If a label looks wrong, the comment is one click away — that is the point.

What this gets wrong

  • Text-only recommendations are under-counted — and we can measure how badly. If someone writes "read Snow Crash, it called all of this" with no link, we miss it. Benchmark: our book ranking overlaps HackerBooks' public top-200 at 29.5%. That is the honest number, and it is why the Books tab carries a caveat. Videos, tools and papers do not have this problem — for those, a link is the recommendation, so recall is essentially complete.
  • Duplicate editions. The same book under two ASINs, a paperback and a hardcover, stays separate. Conservative on purpose, still wrong.
  • Comment upvotes are not in the archive. We can only weight submissions by score, not the replies underneath them.
  • Old links die. Some entities point at pages that no longer exist; the comment that recommended them still does.
  • Sarcasm. The LLM pass catches most of it, not all of it.

Check us

The dataset is a plain CSV: entities.csv — key, type, title, url, mentions, recommends, criticals, distinct recommenders, first and last seen. The pipeline that produced it is a few hundred lines of Python in src/ and runs end to end: download, extract, tag, aggregate, export.

Known benchmark: our book ranking is compared against HackerBooks' public CSV on every build. Current result: 29.5% overlap on their top 200 — reported here rather than hidden, because the failure mode (text-only mentions) is the most useful thing we learned.

What this is not

This site hosts no content. It is an index: every entity links out to the original source, and every row links back to the Hacker News comment that recommended it. Nothing is copied, re-hosted or resold.

No accounts, no tracking, no recommendation algorithm. Nothing is stored about you. There is no "for you" — the entire premise is that the crowd's explicit recommendations, with the receipts attached, beat a model guessing what you will click.
